# 라운지핏 회원·그룹수업 예약 플랫폼 MVP 설계 명세

- 문서 상태: 최종 승인
- 작성일: 2026-07-29
- 대상 기간: 2개월 MVP
- 예산 기준: 2천만 원
- 기술 기준: Next.js App Router, TypeScript, Vercel, Neon PostgreSQL

## 1. 프로젝트 배경과 고객 문제

라운지핏은 필라테스·요가 스튜디오 3개 지점과 약 1,200명의 회원을 운영한다. 현재 예약을 카카오톡, 전화, 엑셀로 나누어 관리하고 있어 다음 문제가 반복된다.

- 같은 수업과 시간대에 정원을 초과한 중복 예약이 발생한다.
- 회원이 자신의 예약과 이용권 잔여 횟수를 직접 확인하기 어렵다.
- 예약과 취소에 따른 이용권 차감·복원을 수기로 처리해 잔여 횟수와 정산이 어긋난다.
- 만석 수업의 대기 순서와 취소 자리를 수기로 관리해야 한다.
- 판매 지점과 실제 이용 지점이 다를 때 매출과 이용 실적을 일관되게 구분하기 어렵다.
- 노쇼 회원에게 이용권을 차감하는 운영 규칙을 시스템으로 강제할 수 없다.

MVP는 회원이 모바일 웹에서 직접 그룹수업을 예약하고, 예약 상태와 이용권 잔여 횟수가 자동으로 일치하며, 만석 수업의 대기 순서를 시스템이 처리하도록 만드는 데 집중한다.

## 2. 프로젝트 목표와 성공 기준

### 2.1 목표

1. 회원이 지점과 수업을 선택해 직접 예약·취소할 수 있게 한다.
2. 예약, 취소, 휴강에 따른 이용권 차감과 복원을 자동화한다.
3. 데이터베이스 트랜잭션과 제약조건으로 정원 초과와 중복 예약을 방지한다.
4. 전 지점 공통 이용권을 지원하면서 매출은 판매 지점, 이용 실적은 수업 지점에 귀속한다.
5. 만석 수업의 선착순 대기, 자동 확정, 30분 수락 제안을 자동화한다.
6. 핵심 업무 완료 후 앱 내부 알림 생성을 시도하고, 후속 구현 단계에서는 중요 알림을 웹 푸시로도 전달한다.

### 2.2 출시 후 첫 달 성공 기준

- 시스템으로 인해 발생한 정원 초과 또는 중복 예약: 0건
- 이용권 원장과 회원에게 표시되는 잔여 횟수 불일치: 0건
- 전체 회원 예약 중 모바일 웹에서 회원이 직접 처리한 비율: 80% 이상

노쇼는 별도로 출석 판정하지 않는다. 정상 진행된 수업의 확정 예약은 실제 참석 여부와 관계없이 이용권 사용과 수업 지점 실적으로 처리한다.

## 3. 구현 우선순위와 범위

Must-have가 완료 조건과 테스트를 모두 통과하기 전에는 후속 기능 구현을 시작하지 않는다. Must-have가 핵심 MVP 제출 기준이며, 후속 기능이 미완료여도 예약·이용권·대기 정합성이 검증되면 핵심 MVP는 성립한다.

### 3.1 Must-have 회원 기능

- 관리자가 등록한 회원의 초대 및 최초 비밀번호 설정
- 휴대폰 번호와 비밀번호 로그인
- 관리자가 생성한 일회용 링크를 통한 비밀번호 재설정
- 반응형 모바일 웹
- 3개 지점의 향후 14일 그룹수업 조회
- 그룹수업 예약, 예약 취소, 만석 수업 대기 신청·취소
- 30분 빈자리 제안 확인 및 수락
- 보유 이용권, 잔여 횟수, 유효기간 확인
- 앱 내부 알림함 조회와 읽음 처리

회원은 직접 가입할 수 없다. 관리자가 회원을 등록하면 시스템이 만료 시각이 있는 일회용 초대 링크를 만든다. 관리자는 이 링크를 복사해 현재 사용하는 연락 수단으로 회원에게 직접 전달한다. 플랫폼은 초대 링크 전달을 위한 카카오톡·문자 API를 호출하지 않는다.

초대 링크는 생성 후 7일 동안 한 번만 사용할 수 있다. 비밀번호를 잊은 회원은 관리자에게 재설정을 요청한다. 관리자는 생성 후 30분 동안 한 번만 사용할 수 있는 비밀번호 재설정 링크를 만들어 같은 방식으로 직접 전달한다. 같은 목적의 새 링크를 만들면 기존 미사용 링크는 즉시 무효화한다. MVP는 이메일·문자·카카오 API를 통한 자동 계정 복구를 제공하지 않는다.

### 3.2 Must-have 관리자와 강사 기능

- 본사 관리자, 지점 관리자, 강사 계정과 권한 구분
- 회원 개별 등록과 일회용 초대 링크 생성
- 지점, 강사, 주간 반복 시간표, 수업 정원 관리
- 날짜별 휴강, 강사, 정원 예외 처리
- 오프라인 결제 완료 후 그룹수업권 발급
- 이용권 발급 시 판매 지점, 실제 결제금액, 횟수, 유효기간 기록
- 수업별 확정 예약과 대기 명단 조회

정원 축소 값은 현재 확정 예약 수와 활성 빈자리 제안 수의 합보다 작을 수 없다. 그보다 적게 운영해야 하면 관리자가 해당 수업을 휴강하고 이용권 복원 절차를 사용한다. 강사 변경은 관리자가 직접 지정하는 날짜별 수정만 제공하며 자동 대체 강사 매칭은 제공하지 않는다.

### 3.3 Must-have 핵심 업무 규칙

- 필라테스와 요가 그룹수업에 공통으로 사용하는 한 종류의 횟수권
- 구매 지점과 무관하게 모든 지점에서 이용 가능
- 매출은 이용권 판매 지점, 이용 실적은 수업 지점에 귀속
- 예약 가능 기간은 수업 시작 14일 전부터 1시간 전까지
- 예약 즉시 이용권 1회 차감
- 수업 시작 2시간 전까지 회원 취소 가능 및 이용권 1회 복원
- 수업 시작 2시간 이내 회원 취소 불가
- 정상 진행 수업의 모든 확정 예약은 이용권 사용과 이용 실적에 포함
- 관리자가 휴강하면 확정 예약의 이용권을 모두 복원하고 대기를 종료

시간 경계는 서버의 Asia/Seoul 기준 시각으로 판단한다. 예약은 `수업 시작 14일 전 <= 현재 시각 < 수업 시작 1시간 전`일 때 허용하고, 회원 취소는 `현재 시각 <= 수업 시작 2시간 전`일 때 허용한다.

### 3.4 Must-have 완료 후 구현하는 기능

다음 항목은 Must-have 완료와 자동 테스트 통과가 확인된 뒤에만 구현한다. 핵심 MVP 정합성이나 무료 배포 동작은 이 기능에 의존하지 않는다.

- Web App Manifest와 Service Worker를 포함한 PWA
- 웹 푸시 권한 안내, 기기 구독 등록·해제, 중요 알림 즉시 푸시
- iPhone 홈 화면 설치 안내
- 기간·지점별 실제 결제 매출, 이용 횟수, 수업별 예약률, 회원별 잔여 이용권 보고서
- 운영 보고 결과 CSV 내보내기
- 실패한 웹 푸시의 고급 자동 재시도와 오래된 구독 정리

운영 보고 CSV 내보내기는 조회 결과를 내려받는 기능이다. 제외 범위인 기존 회원 1,200명 데이터의 CSV 가져오기와는 별개다.

트랜잭션 Outbox 패턴은 핵심 MVP와 위 후속 구현에도 포함하지 않는 안정성 개선 항목이다. 운영에서 알림의 최종 전달 보장이 필요해질 때 별도 변경으로 도입한다.

## 4. MVP 제외 범위

- 개인레슨 예약과 개인레슨권
- 기간제 무제한권과 여러 수업 유형별 이용권
- 온라인 결제, 환불, 결제 취소 연동
- 회원 직접 가입
- iOS·Android 네이티브 앱
- 출석·노쇼 구분과 출석 체크 화면
- 강사 대체 자동 매칭
- 카카오 알림톡과 SMS 발송
- 푸시 실패에 대한 관리자 재발송 화면
- 기존 회원과 이용권의 CSV 일괄 가져오기
- 범용 관리자 감사 이력과 변경 사유 조회 화면
- 고급 매출 분석, 예측, 회계 시스템 연동
- 마이크로서비스, Redis, 메시지 브로커

CSV 회원 데이터 이전과 범용 감사 이력은 이 MVP에서 구현하지 않는다. 샘플 데이터 또는 관리자 개별 등록으로 회원과 이용권을 준비한다. 이용권 잔여 정합성에 필요한 이용권 원장은 범용 감사 이력과 구분되는 핵심 데이터로 MVP에 포함한다.

### 4.1 실제 운영 전 데이터 이전 제약

약 1,200명의 기존 회원으로 실제 운영을 시작하기 전에는 이 MVP와 별도의 데이터 이전 단계가 필요하다. 운영 전환 담당자는 기존 엑셀 원본을 정리하고 회원 중복, 휴대폰 번호, 잔여 횟수, 유효기간, 판매 지점을 검증한 뒤 운영 데이터베이스에 적재하고 총계와 표본을 대조해야 한다.

이 단계는 과제용 MVP의 화면·API·자동화 범위가 아니다. MVP에서는 샘플 데이터 또는 관리자 개별 등록으로 기능을 검증하며, 검증되지 않은 기존 엑셀 파일을 운영 데이터베이스에 직접 넣지 않는다.

## 5. 사용자 역할과 권한

| 역할 | 범위 | 주요 권한 |
| --- | --- | --- |
| 본사 관리자 | 전체 지점 | 지점·직원·회원·시간표·수업·이용권 관리, 후속 구현 후 전체 보고서 조회 |
| 지점 관리자 | 배정된 지점 | 소속 지점의 회원·수업·이용권 발급·예약 명단 관리, 후속 구현 후 지점 보고서 조회 |
| 강사 | 자신이 담당하는 수업 | 담당 수업 일정, 확정 예약 명단, 대기 명단 조회 |
| 회원 | 자신의 데이터 | 수업 조회, 예약·취소, 대기 신청·수락, 이용권·알림 조회 |

현재 운영자는 본사 관리자 권한으로 3개 지점을 관리한다. 지점 관리자와 강사 권한은 계정에 명시적으로 부여한다. 모든 권한 검사는 화면 노출 여부와 관계없이 서버에서 다시 수행한다. 강사는 출석 상태를 입력하거나 이용권을 변경할 수 없다.

## 6. 전체 아키텍처

### 6.1 구조

하나의 Next.js App Router + TypeScript 애플리케이션을 Vercel에 배포하는 모듈형 단일 애플리케이션으로 구성한다. 별도 백엔드 서버나 마이크로서비스는 두지 않는다.

- 회원 화면과 관리자 화면: Next.js Server Components 중심
- 상태 변경: Server Actions 또는 Route Handlers
- 업무 규칙: React 구성요소와 분리된 서버 전용 도메인 모듈
- 데이터 저장: Neon PostgreSQL
- 후속 구현 브라우저 처리: Service Worker
- 후속 구현 푸시 전송: 서버의 Web Push 모듈과 VAPID 키
- 지연 정리: 관련 화면·요청 진입 시 실행하는 서버 도메인 작업
- 선택적 보조 정리: Vercel Cron이 호출하는 보호된 내부 Route Handler

예약 생성 시 정원 확인, 중복 예약 확인, 이용권 선택·차감, 원장 기록, 예약 저장을 하나의 PostgreSQL 트랜잭션으로 처리한다. 예약과 이용권 작업이 성공한 뒤 앱 내부 알림 저장을 시도한다. 후속 웹 푸시 기능이 활성화된 환경에서는 내부 알림 저장에 성공한 중요 알림을 같은 서버 요청의 후처리 단계에서 즉시 전송한다.

Vercel 함수는 무상태로 유지한다. Must-have의 예약, 이용권, 대기, 알림 데이터는 Neon PostgreSQL에 저장한다. 후속 웹 푸시 기능을 구현하면 구독과 발송 상태도 같은 데이터베이스에 저장한다.

대기 규칙의 정확성은 Cron 실행 주기에 의존하지 않는다. 예약 취소 직후 같은 요청에서 다음 대기자를 처리하고, 수락 요청은 서버에서 만료 시각을 재검증하며, 관련 화면과 요청 진입 시 만료 건을 지연 정리한다. 따라서 Vercel Hobby 무료 플랜에서도 핵심 예약·대기 흐름이 동작한다.

### 6.2 일정 표현

주간 반복 시간표는 `ClassTemplate`에 저장한다. 회원의 14일 시간표는 반복 규칙과 날짜별 `ClassOccurrence` 예외를 합성해 표시한다. 예약 시 해당 날짜의 수업 발생 건을 고유한 `시간표 + 날짜` 조합으로 생성하거나 재사용한 뒤 잠그고 정원을 검사한다.

이 방식은 수업 생성용 Cron을 요구하지 않는다. 휴강·강사·정원 변경은 해당 날짜의 `ClassOccurrence`에 명시적으로 저장한다. 반복 시간표 변경은 예약이나 날짜별 예외가 없는 미래 날짜에 적용하며, 이미 예약이 있는 날짜는 개별 수업 변경 절차를 사용한다.

| Branch & Member | 지점, 회원, 직원 기본정보 관리 | 권한 모듈 |

| Pass | 이용권 발급, 유효성, 잔여 횟수, 이용권 원장 | 회원·지점 저장소 |
| Reservation | 정원·중복 검증, 예약·취소, 이용권 차감·복원 | 수업·이용권 모듈 |
| Waitlist | 선착순 대기, 자동 확정, 30분 제안, 만료 | 예약 모듈 |
| In-App Notification | 알림 생성, 목록, 읽음, 연결 화면·만료 시각 | 회원 저장소 |
| Web Push | Must-have 완료 후 구독 등록, 즉시 발송, 발송 상태, mock 모드 | 내부 알림·구독 저장소 |
| Deferred Cleanup | 관련 화면·요청에서 만료 제안 정리와 다음 대기자 처리 | 대기·예약 모듈 |
| Optional Maintenance Jobs | 선택적 Cron 보조 정리와 후속 구현 푸시 재시도 | 대기·푸시 모듈 |
| Reporting | Must-have 완료 후 매출·이용 실적·예약률·잔여 이용권 조회와 CSV 출력 | 읽기 전용 데이터 접근 |

대기 모듈은 예약 레코드를 직접 임의 작성하지 않는다. 자동 확정과 수락은 예약 모듈의 동일한 확정 작업을 호출하므로 일반 예약과 같은 정원·중복·이용권 규칙을 적용한다.

알림 모듈은 예약 트랜잭션의 성공 여부를 결정하지 않는다. 업무 트랜잭션이 끝난 뒤 결과를 전달받아 내부 알림을 처리하며, 후속 기능이 활성화된 경우에만 웹 푸시를 추가 처리한다.

### 8.2 관계와 제약조건

- 한 회원은 여러 이용권을 보유할 수 있다.
- 한 수업 발생 건에는 정원 범위 안에서 여러 예약이 연결된다.
- 한 회원과 한 수업 발생 건의 활성 예약은 하나만 허용한다.
- 한 회원은 시간이 겹치는 두 수업에 동시에 확정 예약될 수 없다. 종료 시각과 다른 수업의 시작 시각이 같으면 겹침으로 보지 않는다.
- 한 회원과 한 수업 발생 건의 활성 대기 신청은 하나만 허용한다.
- `ClassOccurrence`의 `ClassTemplate + 수업 날짜` 조합은 고유하다.
- `Pass.remainingCredits`는 0보다 작아질 수 없다.
- MVP에서 활성 `PassProduct`는 공통 그룹수업권 하나만 허용한다.
- 이용권 증감과 `PassLedger` 기록은 같은 트랜잭션에서 수행한다.
- 한 예약은 하나의 이용권을 사용하며 취소 복원도 같은 이용권에 기록한다.
- 후속 웹 푸시 기능에서 한 알림과 한 푸시 구독의 `PushDelivery`는 하나만 존재한다.
- 앱 내부 알림의 중복 방지 키는 `회원 + 업무 이벤트 + 관련 엔터티`를 유일하게 식별한다.

모든 저장 시각은 UTC로 기록하고 화면과 업무 마감 계산은 Asia/Seoul 시간대로 표시한다. 예약에 사용할 이용권은 예약 시점뿐 아니라 수업 시작 시점에도 유효해야 한다.

## 9. 예약 및 취소 흐름

### 9.1 일반 예약

1. 회원은 현재 시각부터 14일 이내이며 시작 1시간 전보다 이른 수업을 선택한다.
2. 서버는 로그인, 회원 상태, 수업 상태, 예약 가능 시간, 동일 수업 중복과 다른 확정 예약의 시간 겹침 여부를 확인한다.
3. 수업 발생 건을 생성 또는 조회하고 행 잠금으로 동시 예약을 직렬화한다.
4. 확정 예약 수와 유효한 빈자리 제안 수를 합산해 정원을 확인한다.
5. 수업 시작 시점까지 유효한 그룹수업권 중 차감 대상을 선택한다.
6. 하나의 트랜잭션에서 이용권 1회 차감, 원장 기록, 확정 예약 저장을 완료한다.
7. 커밋 후 앱 내부 예약 완료 알림 저장을 시도한다. 후속 웹 푸시 기능이 활성화돼 있으면 저장 성공 직후 푸시를 시도한다.

마지막 한 자리에 여러 요청이 동시에 들어오면 잠금과 정원 재검사를 통과한 한 요청만 확정된다. 같은 예약 요청이 재전송되면 요청 식별자를 기준으로 최초 결과를 반환하고 이용권을 다시 차감하지 않는다.

### 9.2 회원 취소

1. 수업 시작 2시간 전까지 취소할 수 있다.
2. 예약 상태를 회원 취소로 변경하고 예약에 사용한 이용권에 1회를 복원한다.
3. 복원 원장을 같은 트랜잭션에 기록한다.
4. 커밋 직후 같은 서버 요청에서 수업 행을 다시 잠그고 대기 규칙에 따라 다음 대기자를 즉시 처리한다.
5. 대기 처리 성공 여부와 관계없이 앱 내부 예약 취소 알림 저장을 시도한다. 후속 웹 푸시 기능이 활성화돼 있으면 저장 성공 직후 푸시를 시도한다.

취소 트랜잭션은 다음 대기자 처리와 분리한다. 대기 처리에 실패해도 완료된 취소와 이용권 복원은 유지하고 오류를 기록한다. 이후 수업 상세·대기 화면이나 관련 요청이 들어오면 지연 정리가 빈자리를 다시 처리한다.

수업 시작 2시간 이내에는 회원 취소 요청을 거절한다. 수업 시작 2시간 이내에 신규 예약하는 회원은 예약 확정 전에 취소할 수 없다는 안내를 확인한다.

### 9.3 휴강

관리자가 수업을 휴강 처리하면 한 트랜잭션에서 수업 상태를 휴강으로 바꾸고, 모든 확정 예약을 휴강 취소로 변경하며, 각 예약에 사용된 이용권을 복원하고, 대기와 빈자리 제안을 종료한다. 커밋 후 대상 회원별 앱 내부 알림 저장을 시도하며, 후속 웹 푸시 기능이 활성화돼 있으면 저장 성공 직후 푸시를 시도한다.

정상 수업의 시작 시각이 지나면 남아 있는 모든 확정 예약을 실제 수업 지점의 이용 실적으로 계산한다. 별도의 출석 또는 노쇼 상태는 만들지 않는다.

## 10. 이용권 발급·차감·복원 규칙

### 10.1 발급

- 결제는 플랫폼 밖에서 기존 방식으로 받는다.
- 관리자는 결제 완료 후 회원, 판매 지점, 실제 결제금액, 총 횟수, 시작일, 만료일을 입력한다.
- 상품 기본 가격·횟수·유효기간은 자동 표시하되 관리자가 실제 판매 조건으로 수정할 수 있다.
- 발급과 동시에 총 횟수만큼 잔여 횟수를 설정하고 발급 원장을 기록한다.
- 발급된 이용권은 구매 지점과 무관하게 모든 지점의 그룹수업에 사용할 수 있다.

### 10.2 자동 선택과 차감

한 회원이 여러 유효 이용권을 보유하면 수업 시작 시점까지 유효한 이용권 중 만료일이 가장 빠른 것을 사용한다. 만료일이 같으면 발급 시각이 가장 오래된 이용권을 선택한다.

예약 확정 시 1회를 즉시 차감한다. 잔여 횟수 조건부 갱신과 차감 원장 생성을 같은 트랜잭션에서 처리해 한 장의 이용권이 동시에 두 번 사용되지 않게 한다.

### 10.3 복원

- 회원이 수업 시작 2시간 전까지 취소하면 사용한 이용권에 1회를 복원한다.
- 관리자가 휴강하면 취소 시각과 관계없이 사용한 이용권에 1회를 복원한다.
- 회원이 늦게 도착하거나 참석하지 않아도 이용권을 복원하지 않는다.
- 같은 예약에서 복원 원장은 한 번만 생성할 수 있다.

매출은 이용권의 판매 지점과 실제 결제금액을 기준으로 집계한다. 이용 실적은 정상 수업의 확정 예약을 수업 지점 기준으로 집계한다.

## 11. 만석 및 대기 예약 흐름

### 11.1 대기 신청

- 정원이 찬 수업에만 대기 신청을 허용한다.
- 신청 시점에 수업 시작까지 유효한 잔여 이용권이 1회 이상 있어야 한다.
- 대기 신청 자체는 이용권을 차감하거나 횟수를 보류하지 않는다.
- 대기 순서는 신청 시각과 고유 식별자 순으로 고정한다.
- 회원은 직접 대기를 취소할 수 있다.

한 회원은 잔여 이용권이 있으면 여러 수업에 대기할 수 있다. 이용권을 보류하지 않으므로 예약 확정 시점에 잔여 횟수와 유효기간을 다시 확인한다. 다른 예약으로 이용권을 모두 사용한 회원은 확정 대상에서 제외하고 앱 내부 알림으로 이유를 안내한다.

활성 대기자가 있으면 새로 생긴 자리는 대기 순서에 먼저 배정한다. 일반 회원은 대기자를 건너뛰어 직접 예약할 수 없다.

### 11.2 수업 시작 4시간 이전

공석이 생긴 시각이 수업 시작 4시간보다 이전이면 첫 번째 유효 대기자를 즉시 예약으로 확정한다. 예약 모듈이 정원, 시간 겹침, 이용권을 다시 검사하고 이용권을 1회 차감한다. 커밋 후 앱 내부 자동 확정 알림 저장을 시도하며, 후속 웹 푸시 기능이 활성화돼 있으면 저장 성공 직후 푸시를 시도한다.

### 11.3 수업 시작 4시간 이내부터 1시간 전까지

첫 번째 유효 대기자에게 빈자리 수락 제안을 생성하고 자리를 임시 확보한다. 제안 만료 시각은 `제안 생성 시각 + 30분`과 `수업 시작 1시간 전` 중 빠른 시각이다.

앱 내부 알림에는 만료 시각과 수락 화면 링크를 포함하며, 후속 웹 푸시 기능이 활성화돼 있으면 같은 정보를 푸시에도 포함한다. 회원이 수락하면 서버의 데이터베이스 현재 시각으로 제안 만료 시각과 수업 시작 1시간 마감을 먼저 재검증한다. 유효한 경우에만 정원, 시간 겹침, 이용권을 다시 검사하고 이용권 차감과 예약 확정을 한 트랜잭션으로 처리한다. 거절, 만료, 시간 겹침, 이용권 부족이면 자리를 해제하고 같은 요청에서 다음 대기자에게 제안한다.

### 11.4 수업 시작 1시간 전

예약과 대기 승급을 마감한다. 남은 대기와 수락 제안은 만료 처리한다. 만료 이후에는 알림 링크를 열어도 수락할 수 없다.

### 11.5 Cron 없는 지연 정리

회원 수업 목록·수업 상세·대기 수락 화면, 관리자 수업 명단, 예약 취소와 대기 관련 요청에 진입하면 해당 수업의 만료된 제안을 먼저 지연 정리한다. 정리 작업은 수업 행 잠금과 상태 조건을 사용해 만료 처리, 자리 해제, 다음 대기자 처리를 한 번만 수행한다.

지연 정리는 화면 표시를 최신화하기 위한 보완 경로이며, 만료된 제안의 수락 가능 여부는 항상 수락 요청 서버 검증이 최종 결정한다. 선택적 Cron이 실행되지 않아도 만료 제안으로 예약을 확정할 수 없다.

## 12. 앱 내부 알림과 웹 푸시 구조

### 12.1 앱 내부 알림

모든 알림 대상 업무 이벤트는 핵심 업무 트랜잭션을 먼저 커밋한 뒤 웹 서비스 내부 알림함의 `Notification` 저장을 시도한다. 저장에 성공한 알림만 회원의 알림함에 표시한다. 알림은 유형, 제목, 본문, 생성 시각, 읽음 여부, 관련 화면 링크, 선택적 만료 시각을 가진다.

앱 내부 알림 대상은 다음을 포함한다.

- 이용권 발급
- 예약 완료·취소
- 대기 신청·취소
- 자동 예약 확정
- 빈자리 수락 제안·만료
- 수업 휴강 또는 회원 예약에 영향을 주는 변경
- 확정 시 이용권 부족으로 대기 순서에서 제외된 결과

알림 저장 실패는 완료된 예약, 이용권, 대기 상태를 되돌리지 않고 구조화 로그에 남긴다. MVP는 트랜잭션 Outbox나 자동 알림 복구 작업을 구현하지 않으므로 실패한 알림의 최종 저장을 보장하지 않는다. 최종 저장 보장이 운영 요구사항이 되면 별도 안정성 개선으로 Outbox를 도입한다.

### 12.2 Must-have 완료 후 웹 푸시 대상과 즉시 발송

다음 중요 알림은 앱 내부 알림 저장에 성공한 직후 활성 푸시 구독으로 발송을 시도한다.

- 예약 완료
- 예약 취소
- 자동 예약 확정
- 빈자리 수락 요청
- 수업 휴강 또는 예약에 영향을 주는 변경

웹 푸시 payload에는 알림 고유 식별자, 짧은 메시지, 관련 화면 경로, 선택적 만료 시각만 포함한다. 회원의 상세 개인정보는 포함하지 않는다.

`PushDelivery`의 `Notification + PushSubscription` 고유 제약과 조건부 상태 전이로 같은 알림의 병렬 중복 발송을 막는다. Service Worker는 알림 고유 식별자를 브라우저 notification tag로 사용해 재시도된 같은 알림이 별도 항목으로 누적되지 않게 한다.

### 12.3 실패 격리

앱 내부 알림 저장 실패와 웹 푸시 실패는 예약, 이용권, 대기 상태를 변경하지 않는다. 웹 푸시의 일시적 실패는 발송 상태에 기록하고, 만료되거나 해지된 구독은 비활성화한다. 고급 자동 재시도를 구현한 경우에만 선택적 Cron에서 재시도하며, 카카오 알림톡이나 SMS로 전환하지 않는다.

## 13. Must-have 완료 후 Web Push 구독 및 Service Worker 처리

이 절 전체는 예약·이용권·대기 Must-have가 완료되고 자동 테스트를 통과한 뒤 구현한다. 이 기능이 없거나 브라우저가 지원하지 않아도 앱 내부 알림과 핵심 예약 기능은 동작한다.

### 13.1 권한과 구독

1. 회원 최초 로그인 후 알림 기능과 사용 목적을 설명한다.
2. 회원이 명시적인 허용 버튼을 누르면 브라우저 알림 권한을 요청한다.
3. 권한이 허용되면 Service Worker를 등록하고 Push API 구독을 생성한다.
4. endpoint, `p256dh`, `auth` 키를 회원·기기별 구독으로 서버에 저장한다.
5. 이미 같은 endpoint가 있으면 새 행을 만들지 않고 활성 상태와 키를 갱신한다.

권한 거부, 미지원 브라우저, 구독 실패는 예약 사용을 막지 않는다. 해당 회원에게는 앱 내부 알림만 제공한다.

iPhone 웹 푸시 지원 대상은 iOS 16.4 이상에서 홈 화면에 추가해 실행한 웹 앱이다. iPhone 브라우저에서 독립 실행 상태가 아니면 홈 화면 추가 절차를 안내하고, 설치된 웹 앱에서 회원 동작을 통해 권한을 요청한다. 이 조건을 충족하지 않으면 앱 내부 알림만 제공한다.

### 13.2 수신과 이동

Service Worker가 푸시를 받으면 payload의 알림 고유 식별자를 tag로 사용해 휴대폰 알림 영역에 표시한다. 회원이 알림을 누르면 동일 출처의 열린 창을 찾아 해당 예약 또는 대기 수락 경로로 이동하고, 열린 창이 없으면 새 창을 연다.

대기 수락 알림은 절대 만료 시각을 전달한다. 화면은 서버 시각으로 수락 가능 여부를 다시 확인하며, 브라우저에 표시된 카운트다운만으로 수락을 승인하지 않는다.

### 13.3 개발·테스트 mock 모드

mock 모드에서는 실제 Push API endpoint로 네트워크 요청을 보내지 않는다. 동일한 payload 생성, 발송 상태 전이와 실패 분기를 실행하고 결과를 테스트 저장소와 로그에서 검증한다. 고급 자동 재시도를 구현한 경우에는 재시도 분기도 mock으로 검증한다.

## 14. 지연 정리와 선택적 Vercel Cron

### 14.1 무료 티어 핵심 처리

Must-have 대기 처리는 Cron에 의존하지 않는다.

1. 회원 예약 취소가 커밋되면 같은 요청에서 다음 대기자 처리를 즉시 호출한다.
2. 빈자리 제안 수락 시 데이터베이스 현재 시각으로 실제 만료 시각과 수업 시작 1시간 마감을 재검증한다.
3. 수업·대기 관련 화면이나 요청에 진입하면 해당 수업의 만료 제안을 지연 정리한다.
4. 모든 정리와 승급은 행 잠금, 현재 상태 조건, 고유 제약조건으로 중복 실행을 방지한다.

따라서 Vercel Hobby에서 잦은 Cron을 제공하지 않아도 만료된 제안이 수락되거나 대기 순서가 무시되지 않는다. 아무 요청도 없는 동안 화면상 만료 상태 정리가 늦어질 수 있지만, 다음 관련 요청에서 정리되며 수락 서버 검증은 항상 정확한 시각을 적용한다.

### 14.2 선택적 보조 Cron

Vercel Cron은 배포 플랜이 허용하는 낮은 빈도로 실행하는 선택적 보조 작업이다. 다음 항목의 일괄 정리만 담당하며 핵심 예약·대기 정확성의 전제조건이 아니다.

- 요청이 없어 남아 있는 만료 제안 정리
- 후속 웹 푸시 기능의 재시도 가능 실패 처리
- 비활성 푸시 구독 정리

같은 Cron 실행이 겹치거나 다시 실행돼도 데이터베이스 현재 시각, 조건부 상태 전이, 고유 제약조건으로 한 번만 처리한다. Cron Route Handler는 전용 비밀값을 검증한다.

후속 웹 푸시의 고급 재시도를 구현하면 네트워크·서버 오류만 최대 3회 재시도하고, 구독 만료·해지 응답은 즉시 비활성화한다. Hobby에서는 재시도 시각을 보장하지 않고 가능한 Cron 실행 때 처리한다. 1분 간격의 만료 정리나 푸시 재시도가 운영 요구사항이 되면 Vercel Pro 이상 플랜이 필요하다.

## 15. 오류 처리

### 15.1 예상 가능한 업무 오류

정원 초과, 중복 예약, 이용권 부족·만료, 예약·취소 마감, 만료된 대기 제안은 사용자에게 구체적인 메시지로 안내한다. 검증 중 하나라도 실패하면 예약과 이용권 트랜잭션 전체를 롤백한다.

### 15.2 동시 요청과 멱등성

- 마지막 자리 경쟁은 수업 발생 건 잠금 후 정원 재검사로 한 요청만 확정한다.
- 이용권 차감은 잔여 횟수 조건부 갱신으로 음수 값을 방지한다.
- 예약 요청 식별자와 데이터베이스 고유 제약조건으로 중복 클릭·재전송을 한 번만 처리한다.
- 취소 복원과 휴강 복원은 예약별 원장 유형 고유 제약으로 중복 복원을 막는다.
- 대기 승급과 제안 만료는 현재 상태를 조건으로 갱신한다.

### 15.3 앱 내부 알림 오류

앱 내부 알림은 핵심 업무 트랜잭션 커밋 후 생성한다. 저장 실패가 발생해도 이미 완료된 예약, 이용권, 대기 상태를 되돌리지 않는다.

실패 로그에는 알림 유형, 관련 업무 식별자, 회원 식별자, 실패 시각, 오류 유형만 기록한다. 비밀번호, 푸시 암호화 키, 알림 본문 전체와 기타 개인정보는 기록하지 않는다. MVP에는 실패 알림 조회, 자동 복구, 수동 재생성, 관리자 재발송 화면이 없으므로 알림의 최종 저장을 보장하지 않는다. 최종 저장 보장을 위한 트랜잭션 Outbox는 후속 안정성 개선 항목이다.

### 15.4 Must-have 완료 후 웹 푸시 오류

앱 내부 알림 저장에 성공한 경우에만 웹 푸시를 시도한다. 푸시 실패는 핵심 업무와 내부 알림을 변경하지 않고 발송 상태와 로그에 남긴다. 고급 자동 재시도를 구현한 경우에만 일시 실패를 선택적 Cron의 재시도 대상으로 처리하며, 재시도 한도를 넘으면 최종 실패로 남긴다. 최종 실패 상태는 서버 로그와 데이터에만 남으며 관리자 화면에서 재발송하지 않는다.

권한 거부와 미지원 브라우저는 오류가 아니라 내부 알림 전용 상태로 취급한다. Service Worker 등록이나 구독 생성 실패도 회원의 예약 기능을 막지 않는다.

### 15.5 데이터베이스와 서버 오류

Neon 연결 또는 Vercel 함수 오류로 핵심 트랜잭션을 완료하지 못하면 변경사항을 커밋하지 않고 재시도를 안내한다. 서버 로그는 요청 식별자와 오류 유형을 포함하되 민감정보를 제외한다.

## 16. 보안 및 개인정보 최소화 원칙

- 휴대폰 번호는 로그인과 회원 식별에 필요한 범위에서만 수집한다.
- 비밀번호는 강한 단방향 솔트 해시로 저장하며 평문으로 저장하거나 로그에 남기지 않는다.
- 로그인 세션은 Secure, HttpOnly, SameSite 속성이 있는 쿠키로 관리한다.
- 모든 상태 변경은 인증, 역할, 소유권, 요청 출처를 서버에서 검증한다.
- 본사 관리자만 전체 지점 데이터에 접근하고 지점 관리자는 배정 지점으로 제한한다.
- Neon 연결은 암호화된 연결을 사용하고 데이터베이스 자격증명은 Vercel 환경변수로 관리한다.
- VAPID 개인키, 선택적 Cron 비밀값, 세션 비밀값은 클라이언트 번들에 포함하지 않는다.
- 푸시 구독 endpoint와 암호화 키는 발송에만 사용하며 화면이나 일반 로그에 노출하지 않는다.
- 웹 푸시 payload에는 회원명, 휴대폰 번호, 결제금액을 포함하지 않는다.
- 후속 웹 푸시 기능에서 비활성 구독은 발송 대상에서 즉시 제외한다. 비활성화 후 30일이 지난 구독은 선택적 정리 작업의 다음 실행 때 삭제하며 정확한 삭제 시각은 보장하지 않는다.
- 앱 내부 알림과 업무 로그에는 목적에 필요한 식별자와 상태만 기록한다.

## 17. 테스트 전략

Must-have 테스트는 Cron을 완전히 비활성화한 환경에서 통과해야 한다. 웹 푸시, 보고서, 고급 재시도 테스트는 Must-have 검증이 끝난 뒤 해당 기능을 구현할 때 추가한다.

### 17.1 Must-have 단위 테스트

Vitest로 다음 업무 규칙을 데이터베이스와 화면 없이 검증한다.

- 이용권 만료일·발급일 우선 선택
- 예약 14일 오픈, 1시간 마감, 2시간 취소 마감
- 4시간 자동 확정, 30분 제안, 1시간 대기 종료
- 제안 만료 시각의 `30분`과 `수업 1시간 전` 최솟값 계산
- 서버 현재 시각 기준의 만료 제안 수락 거절
- 역할별 접근 권한

테스트에서 현재 시각을 주입해 실제 대기 없이 모든 시간 경계를 검증한다.

### 17.2 Must-have PostgreSQL 통합 테스트

격리된 테스트 데이터베이스에서 실제 트랜잭션과 제약조건을 검증한다.

- 예약과 차감이 함께 성공하거나 함께 롤백
- 취소·휴강과 복원이 함께 성공하거나 함께 롤백
- 같은 회원의 동일 수업 중복 예약 차단
- 같은 회원의 시간이 겹치는 수업 동시 예약 차단
- 마지막 한 자리 동시 예약 시 한 명만 확정
- 같은 이용권에 대한 동시 차감 시 한 번만 성공
- 이용권 원장 합계와 잔여 횟수 일치
- 대기 자동 확정, 제안, 수락, 만료의 상태 전이
- 예약 취소 커밋 직후 다음 대기자 자동 확정 또는 수락 제안 생성
- Cron 비활성 상태에서 만료 제안 수락 거절
- 관련 화면·요청 진입 시 만료 제안 지연 정리와 다음 대기자 처리
- 지연 정리 반복 실행 시 중복 승급·중복 복원 방지

### 17.3 Must-have 앱 내부 알림 테스트

- 핵심 업무 커밋 후 앱 내부 알림 저장 시도
- 저장 성공 시 회원 알림함 표시와 읽음 처리
- 알림 저장을 강제로 실패시켜도 예약·이용권·대기 상태 유지와 실패 로그 생성
- 같은 업무 이벤트를 다시 처리해도 내부 알림 중복 저장 방지
- Outbox나 Cron 없이 실패 알림이 핵심 업무에 영향을 주지 않음

### 17.4 Must-have 브라우저 테스트

Playwright로 다음 핵심 흐름을 검증한다.

- 회원 로그인 → 수업 예약 → 이용권 감소 → 정상 취소 → 복원
- 만석 수업 대기 → 자동 확정
- 만석 수업 대기 → 30분 제안 → 알림 클릭 → 수락
- Cron 비활성 상태에서 예약 취소 → 다음 대기자 즉시 처리
- Cron 비활성 상태에서 만료된 제안 링크 → 서버 거절
- Cron 비활성 상태에서 관련 화면 진입 → 만료 제안 정리 → 다음 대기자 처리
- 관리자 휴강 → 예약 취소 → 이용권 복원 → 대기 종료
- 앱 내부 알림함 조회와 알림 링크 이동
- 권한이 없는 사용자의 관리자 기능 접근 차단

### 17.5 Must-have 완료 후 기능 테스트

- 웹 푸시 대상 알림 분류, payload, 연결 경로, 만료 시각
- 앱 내부 알림 저장 성공 후에만 웹 푸시 시도
- 푸시 실패가 예약·이용권·대기·내부 알림에 영향을 주지 않음
- 알림·구독별 발송 레코드 고유성과 Service Worker tag를 통한 중복 표시 방지
- mock 모드에서 실제 푸시 endpoint를 호출하지 않고 발송 상태 검증
- 권한 허용 시 Service Worker·구독 등록, 권한 거부·미지원·구독 없음 시 내부 알림만 제공
- Android Chrome 알림 수신과 클릭 이동
- iPhone 홈 화면 설치 안내, 설치 후 권한 요청, 알림 수신과 클릭 이동
- 고급 재시도 구현 시 일시 실패 최대 3회 재시도, 영구 실패 종료, 반복 Cron의 중복 발송 방지
- 만료·해지 구독 비활성화와 선택적 정리
- 기간·지점별 보고서 집계와 운영 보고 CSV 출력

웹 푸시 자동 테스트는 mock 모드로 실행하며 실제 푸시 endpoint를 호출하지 않는다.

### 17.6 CI와 수동 기기 확인

Must-have CI는 TypeScript 검사, 단위 테스트, PostgreSQL 통합 테스트, Playwright 핵심 흐름을 Cron 비활성 상태로 실행한다. 후속 기능을 구현하면 관련 자동 테스트를 같은 CI에 추가한다. 실제 웹 푸시는 Vercel HTTPS 배포에서 전용 테스트 계정으로 Android Chrome과 홈 화면에 설치한 iPhone에서 각각 수동 확인한다.

카카오 알림톡, SMS, 회원 CSV 가져오기, 범용 감사 이력은 테스트 대상에 포함하지 않는다.

## 18. 배포 구조

### 18.1 Vercel

Vercel Hobby의 하나의 프로젝트만으로 Must-have를 배포할 수 있다. Must-have는 다음을 제공하며 Cron 작업을 요구하지 않는다.

- Next.js 회원·관리자 화면
- Server Actions와 Route Handlers
- 예약 취소 직후 대기자 처리와 요청 진입 시 지연 정리

Must-have 완료 후 같은 프로젝트에 Service Worker, Web App Manifest, 즉시 웹 푸시 발송을 추가한다. 보호된 Cron Route Handler는 배포 플랜이 허용하는 빈도로 보조 정리가 필요할 때만 선택적으로 배포한다.

Vercel Hobby에서는 핵심 흐름이 Cron 없이 동작하며, 보조 Cron의 정확한 실행 시각에 의존하지 않는다. 1분 간격의 만료 정리 또는 푸시 재시도가 운영 요구사항이면 Vercel Pro 이상 플랜으로 전환해야 한다.

### 18.2 Neon PostgreSQL

Neon은 회원, 지점, 시간표, 수업 발생 건, 이용권, 원장, 예약, 대기, 앱 내부 알림을 저장한다. Must-have 완료 후 웹 푸시를 구현하면 푸시 구독과 발송 상태도 저장한다. 개발·미리보기·운영 환경은 서로 다른 Neon 데이터베이스 또는 브랜치를 사용해 테스트 데이터가 운영 데이터와 섞이지 않게 한다.

### 18.3 환경변수

Must-have 환경에서는 다음 비밀 설정을 Vercel에서 관리한다.

- Neon 데이터베이스 연결 문자열
- 인증·세션 비밀값

웹 푸시와 선택적 Cron을 구현한 환경에서는 다음 설정을 추가한다.

- VAPID 공개키와 개인키
- Cron 호출 검증 비밀값
- 웹 푸시 실제 발송·mock 모드 설정

VAPID 공개키만 푸시 구독 생성을 위해 클라이언트에 제공한다. 개인키와 데이터베이스 자격증명은 서버에서만 사용한다.

## 19. 완료 조건과 수동 검증 항목

### 19.1 Must-have 완료 조건

- 회원이 향후 14일 수업을 조회하고 예약·취소할 수 있다.
- 예약과 이용권 차감, 취소·휴강과 복원이 트랜잭션으로 일치한다.
- 정원 초과, 중복 예약, 이용권 중복 차감이 데이터베이스 수준에서 방지된다.
- 전 지점 공통 이용권을 사용할 수 있고, 판매 지점과 실제 이용 지점에 귀속될 데이터가 분리 기록된다.
- 만석 수업의 자동 확정과 30분 수락 제안이 정해진 시간 규칙대로 동작한다.
- 예약 취소 직후 다음 대기자를 처리하고, 제안 수락 시 서버가 실제 만료 시각을 재검증한다.
- 관련 화면·요청 진입 시 만료 제안을 지연 정리하며, 이 흐름 전체가 Cron 비활성 상태에서 동작한다.
- 핵심 업무 커밋 후 앱 내부 알림 저장을 시도하고, 성공한 알림은 알림함에 표시한다.
- 앱 내부 알림 저장 실패가 핵심 업무를 되돌리지 않고 개인정보를 제외한 구조화 로그에 남는다.
- 본사 관리자·지점 관리자·강사·회원 권한이 서버에서 강제된다.
- 자동 테스트와 TypeScript 검사가 통과하고 Vercel 배포가 완료된다.

### 19.2 Must-have 완료 후 기능 검증 조건

다음 조건은 해당 후속 기능을 구현한 경우에 적용하며 Must-have 완료 판정을 막지 않는다.

- 중요 알림은 앱 내부 알림 저장 성공 직후 웹 푸시로 발송을 시도한다.
- 푸시 실패는 예약·이용권·대기·앱 내부 알림을 되돌리지 않는다.
- 푸시 권한 거부·미지원·구독 없음 상태에서는 앱 내부 알림만 제공한다.
- 알림 고유 식별자와 발송 상태로 웹 푸시의 중복 전송을 방지한다.
- 고급 재시도를 구현하면 선택적 Cron의 중복 실행에도 발송과 상태 전이가 한 번만 적용된다.
- 기간·지점별 보고서와 운영 보고 CSV가 판매 지점 매출과 실제 수업 지점 이용 실적을 분리해 집계한다.

### 19.3 Must-have 수동 검증 항목

1. 두 브라우저에서 마지막 한 자리를 동시에 예약해 한 명만 확정되는지 확인한다.
2. 한 회원의 이용권을 동시에 사용하는 요청에서 잔여 횟수가 음수가 되지 않는지 확인한다.
3. 같은 회원이 시간이 겹치는 두 수업을 예약할 수 없고, 앞 수업 종료와 다음 수업 시작이 같은 경우에는 예약 가능한지 확인한다.
4. 수업 시작 4시간 이전 자동 확정과 4시간 이내 30분 제안이 각각 동작하는지 확인한다.
5. 30분이 지나거나 수업 시작 1시간 전이 되면 제안 링크가 거절되는지 확인한다.
6. 관리자가 휴강했을 때 확정 예약 전체의 이용권이 한 번씩 복원되고 대기가 종료되는지 확인한다.
7. 다른 지점에서 구매한 이용권으로 예약하고 판매 지점과 실제 수업 지점이 서로 다른 값으로 기록되는지 데이터에서 확인한다.
8. Cron을 비활성화하고 예약을 취소해 다음 대기자가 즉시 자동 확정되거나 제안을 받는지 확인한다.
9. Cron을 비활성화하고 만료된 제안 수락을 요청해 서버가 거절하는지 확인한다.
10. Cron을 비활성화하고 관련 화면에 진입해 만료 제안 정리와 다음 대기자 처리가 실행되는지 확인한다.
11. 앱 내부 알림 저장 실패를 발생시켜 예약·이용권·대기 상태가 유지되고 구조화 로그가 남는지 확인한다.
12. 강사가 담당하지 않은 수업이나 이용권 관리 기능에 접근할 수 없는지 확인한다.
13. 기존 회원 CSV 가져오기 화면이나 API가 없고, 실제 1,200명 운영 전 별도 데이터 이전이 필요하다는 운영 문서가 명시되어 있는지 확인한다.

### 19.4 Must-have 완료 후 수동 검증 항목

1. 푸시 권한을 거부한 회원이 앱 내부 알림만 정상적으로 받는지 확인한다.
2. 웹 푸시 실패를 발생시켜 예약·이용권·대기·앱 내부 알림 상태가 유지되는지 확인한다.
3. 같은 알림 재시도 시 휴대폰 알림 영역에 중복 항목이 쌓이지 않는지 확인한다.
4. Android Chrome에서 웹 푸시 수신과 알림 클릭 이동을 확인한다.
5. iPhone에서 홈 화면 설치 안내, 설치 후 권한 요청, 웹 푸시 수신과 알림 클릭 이동을 확인한다.
6. 만료된 푸시 구독이 비활성화되고 재시도 대상에서 제외되는지 확인한다.
7. 운영 보고 CSV 출력과 제외된 회원 데이터 CSV 가져오기가 혼동되지 않는지 확인한다.

출시 후 첫 달에는 중복 예약 0건, 이용권 잔여 불일치 0건, 회원 직접 예약률 80% 이상을 운영 지표로 확인한다.

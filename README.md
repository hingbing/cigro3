# LoungeFit

> 회원·수업·이용권·예약을 한 곳에서 관리할 수 있는 피트니스 센터 예약 관리 MVP

## Live Demo

- 배포 URL: https://loungefit-iui5vacpg-hingbing-s-projects.vercel.app/login
- 배포 환경: Vercel + Neon PostgreSQL

## 프로젝트 실행 방법

### 1. 저장소 복제

```bash
git clone <repository-url>
cd loungefit-mvp
```

### 2. 패키지 설치

```bash
npm install
```

### 3. 환경변수 설정

프로젝트 루트에 `.env.local` 파일을 생성합니다.

```env
DATABASE_URL=postgresql://사용자:비밀번호@호스트:포트/데이터베이스
SESSION_SECRET=32자 이상의 충분히 긴 랜덤 문자열
```

테스트 데이터베이스를 사용할 경우 `.env.test.example`을 복사해 `.env.test`를 생성합니다.

```bash
cp .env.test.example .env.test
```

Windows PowerShell:

```powershell
Copy-Item .env.test.example .env.test
```

### 4. 테스트용 PostgreSQL 실행

Docker가 설치되어 있어야 합니다.

```bash
docker compose up -d
```

### 5. 데이터베이스 마이그레이션

테스트 데이터베이스:

```bash
npm run db:migrate:test
```

운영 또는 별도 데이터베이스:

```bash
npx drizzle-kit migrate
```

운영 DB 마이그레이션 시 다음 환경변수를 사용합니다.

```env
DATABASE_URL_MIGRATIONS=postgresql://...
```

### 6. 데모 데이터 생성

```bash
npm run seed:demo
```

생성되는 데모 계정:

```text
관리자: 010-9999-9999 / admin-password
회원: 010-1234-5678 / demo-password
```

### 7. 개발 서버 실행

```bash
npm run dev
```

브라우저에서 다음 주소로 접속합니다.

```text
http://localhost:3000
```

## 프로젝트 소개

LoungeFit은 여러 지점을 운영하는 피트니스 센터를 위한 회원 및 수업 예약 관리 서비스입니다.

회원은 보유 이용권을 확인하고 원하는 지점과 수업을 선택해 예약할 수 있습니다. 관리자는 회원과 수업 일정을 조회하고 새로운 수업을 등록할 수 있습니다.

이번 프로젝트는 모든 기능을 한 번에 구현하기보다, 실제 사용 흐름에서 가장 중요한 기능을 먼저 사용할 수 있는 형태로 완성하는 것을 목표로 했습니다.

### 해결하고자 한 문제

기존에 회원, 수업 일정, 예약 현황과 이용권 정보가 분리되어 관리될 경우 다음과 같은 문제가 발생할 수 있습니다.

- 회원이 자신의 남은 이용권을 바로 확인하기 어렵다.
- 수업의 정원과 현재 예약 인원을 실시간으로 확인하기 어렵다.
- 예약과 이용권 차감이 별도로 처리되면 데이터가 맞지 않을 수 있다.
- 지점별 회원과 수업을 일관된 방식으로 관리하기 어렵다.
- 관리자가 수업 운영 현황을 한눈에 확인하기 어렵다.

LoungeFit은 이러한 정보를 하나의 서비스 안에서 연결해 관리할 수 있도록 설계했습니다.

## 가상 고객 상담 및 요구사항 정리

과제에서 제공된 가상 고객사 중 **라운지핏**을 선택했습니다.

상담 과정에서는 기능을 바로 구현하기보다 먼저 고객의 핵심 업무 흐름을 파악하는 데 집중했습니다.

### 핵심 사용자

#### 회원

- 로그인
- 보유 이용권 확인
- 지점 및 수업 조회
- 수업 예약
- 나의 예약 조회
- 예약 취소

#### 관리자

- 관리자 로그인
- 회원 목록 조회
- 회원 상세 정보 확인
- 수업 일정 조회
- 수업 등록
- 지점별 운영 정보 확인

### 핵심 업무 규칙

- 회원은 남은 이용권이 있어야 수업을 예약할 수 있다.
- 수업 정원을 초과해서 예약할 수 없다.
- 동일한 수업을 중복 예약할 수 없다.
- 예약이 완료되면 이용권이 차감된다.
- 예약을 취소하면 이용권이 복원된다.
- 관리자는 허용된 관리 기능에만 접근할 수 있다.

## 개발 접근 방식

이번 프로젝트는 바로 코드를 작성하는 방식이 아니라, **Superpowers 기반의 계획 중심 개발 방식**으로 진행했습니다.

### 1. 요구사항 분석

먼저 가상 고객과의 상담을 통해 사용자의 역할과 핵심 업무 흐름을 정리했습니다.

기능 목록만 나열하지 않고 다음 내용을 함께 정의했습니다.

- 누가 사용하는 기능인지
- 어떤 조건에서 실행되는지
- 성공했을 때 데이터가 어떻게 변경되는지
- 실패할 수 있는 상황은 무엇인지
- 관리자와 일반 회원의 권한 차이는 무엇인지

### 2. 구현 계획 작성

전체 기능을 작은 작업 단위로 분리한 구현 계획을 먼저 작성했습니다.

계획에는 다음 내용을 포함했습니다.

- 데이터베이스 구조
- 인증 및 세션 처리 방식
- 회원과 관리자 권한 구분
- 이용권과 예약의 관계
- 예약 및 취소 시 데이터 처리 순서
- 화면별 구현 범위
- 단위 테스트와 통합 테스트 대상
- 배포 환경 구성

구현 계획 문서:

```text
docs/superpowers/plans/2026-07-29-loungefit-mvp.md
```

### 3. 단계별 구현

구현 계획을 기준으로 기능을 작은 작업 단위로 나누어 순차적으로 개발했습니다.

각 단계에서는 다음 흐름을 따랐습니다.

1. 구현할 동작 정의
2. 필요한 데이터 구조 확인
3. 실패 가능한 상황 정리
4. 기능 구현
5. 테스트 및 타입 검사
6. 다음 작업으로 이동

이를 통해 기능 간 의존성을 줄이고, 문제가 발생했을 때 원인을 좁히기 쉽도록 했습니다.

### 4. MVP 범위 조절

제한된 시간 안에 실제로 사용할 수 있는 결과물을 만드는 것을 우선했습니다.

따라서 핵심 흐름인 다음 기능을 우선 구현했습니다.

```text
로그인
→ 수업 조회
→ 이용권 확인
→ 수업 예약
→ 예약 내역 확인
→ 예약 취소
```

알림, 자동 대기 승급, 결제 등 외부 시스템 연동이 필요한 기능은 향후 개발 범위로 분리했습니다.

## 핵심 설계 결정

### 예약과 이용권 차감을 하나의 작업으로 처리

예약 정보만 저장되고 이용권이 차감되지 않거나, 반대로 이용권만 차감되는 문제가 발생하지 않도록 예약 생성과 이용권 차감을 하나의 데이터베이스 트랜잭션으로 처리했습니다.

### 예약 취소와 이용권 복원 연결

예약 취소 시 예약 상태 변경과 이용권 복원이 함께 처리되도록 구성했습니다.

### 서버에서 권한 검사

화면에서 관리자 메뉴를 숨기는 것만으로는 충분하지 않기 때문에, 서버에서도 사용자 역할과 접근 권한을 확인하도록 했습니다.

### 데이터베이스 제약조건 활용

애플리케이션 코드뿐 아니라 데이터베이스에서도 잘못된 데이터가 들어가지 않도록 제약조건을 사용했습니다.

예를 들어 다음 상황을 방지합니다.

- 동일 회원의 동일 수업 중복 예약
- 잘못된 역할 값 저장
- 관련 데이터가 없는 예약 생성
- 유효하지 않은 예약 상태 저장

### 시간대 처리

수업 시간은 일관된 기준으로 저장하고, 사용자 화면에서는 한국 시간에 맞게 표시하도록 고려했습니다.

### MVP 중심 구현

실제 사용자 흐름과 직접 관련된 기능을 우선 구현했습니다. 복잡도가 높고 외부 연동이 필요한 기능은 핵심 예약 흐름과 분리해 향후 기능으로 정리했습니다.

## 개발 과정에서 배운 점

이번 프로젝트를 통해 단순히 화면을 만드는 것보다 **업무 규칙과 데이터 정합성을 먼저 정의하는 것이 중요하다**는 점을 배웠습니다.

특히 예약 기능은 버튼을 눌러 데이터를 한 건 추가하는 것으로 끝나지 않았습니다.

예약 시에는 다음 조건을 함께 고려해야 했습니다.

- 사용자가 로그인되어 있는가
- 유효한 이용권을 보유하고 있는가
- 남은 이용 횟수가 있는가
- 수업 정원이 남아 있는가
- 이미 같은 수업을 예약하지 않았는가
- 예약과 이용권 차감이 모두 성공했는가

또한 Superpowers 기반으로 구현 전 계획을 작성하고 작업을 작은 단위로 분리하면서, 즉흥적으로 코드를 추가하는 것보다 전체 구조를 유지하기 쉬웠습니다.

시간이 제한된 상황에서는 모든 기능을 구현하기보다, 핵심 사용자 흐름을 먼저 완성하고 나머지 기능을 명확하게 향후 범위로 분리하는 것이 중요하다는 점도 경험했습니다.

## 한계 및 개선점

현재 버전은 과제 제출을 위한 MVP이므로 다음 한계가 있습니다.

- 실제 문자 또는 이메일 알림이 연결되어 있지 않습니다.
- 온라인 결제 기능이 없습니다.
- 회원이 직접 가입하는 기능은 제한적입니다.
- 대기 신청 자동 승급이 구현되어 있지 않습니다.
- 운영자용 통계 대시보드가 없습니다.
- 강사 전용 계정과 화면이 분리되어 있지 않습니다.

향후에는 실제 센터 운영 흐름을 추가로 조사한 뒤 기능 우선순위를 다시 정하고 확장할 예정입니다.
